# Router/shared scheduling diagnostic

The pure planner derives a permutation from the validated canonical Gemma SSA and its reusable RMS statistics plan. It preserves the canonical schedule and digest. The shared input normalization remains first, including its original cached-statistics computation. Router normalization, scale and projection move ahead of the shared MLP, and only the two router input versions move to a synthetic dedicated routerIn buffer. Shared gate/up/activation/down/postnorm follow, then the unchanged CPU router top-k and routed-expert branch.

The analyzer checks exact per-layer windows, geometry, tensor names, value lifetimes, byte ranges and statistics actions. A shared physical-buffer mapping is used by both the executor and the planner, including the gate/up slices of the fused GU buffer. It replays all modeled operations in the original and permuted orders. A negative control without routerIn must fail at the first shared gate because the router clobbers its normalized input. Decoded plans require reverify before use.

The proof covers declared interpreter bindings, byte ranges, logical cache/routing states and statistics slots. It does not prove internal effects of runner primitives or GPU ordering. Runtime integration must allocate genuinely separate scratch, verify actual aliases and shared-primitive write effects, and explicitly order asynchronous command buffers. This is currently an experimental pure analysis; no overlap execution, artifact activation or speedup has been validated.

The proposed runtime keeps par64 attention, v1 E4R32 MoE and every modern setting. It keeps CPU FP64 softmax, deterministic ties and renormalization. It retains all 30 router waits and adds 30 command buffers per token, attempting to overlap host turnaround with the shared MLP. Whether the extra submissions help remains unmeasured. Source counts are not per-site elapsed-time attribution, and GPU command-buffer spans are not utilization.

Source and tests were authored by the existing authorized Opus 5.5 CLI.

The first diagnostic runtime implementation compiles natively. The shared ticket ledger, scope predicates, prepared binding checks, buffer extent checks and token counter expectations passed 135 pure tests; the original planner passed all 334 regression checks against the actual canonical graph. These checks create no Metal device and read no model weights. They do not establish hardware correctness or a performance gain.

Independent runtime review requested changes before hardware qualification: failed command drains must prevent reuse of their state and event, asynchronous command-buffer intervals must be reported separately from existing GPU timing, and scope descriptions must match the actual guarded operations. The possible behavior of lower GPU event signals after a CPU cleanup signal remains a review hypothesis, not an observed failure. The author is implementing fail-closed recovery and regression coverage. A separate small Metal event harness has compiled but has not run; its completion marker and cleanup are also under review. Neither the model harness nor this pass has qualified or changed the serving default.

The corrected runtime passed 170 shared-logic pure tests and all 334 planner regression checks. The complete native package build passed, and the independent runtime reviewer accepted the correction. A failed ticket now poisons its ledger and blocks further overlap operations while retaining scope guards; cleanup drains every committed ticket and preserves the original body error. The next scope entry replaces a fully drained poisoned state with a new event, ledger and router input buffer. Command-buffer intervals accumulate separately and may include event waits; the original GPU timing counter omits these asynchronous intervals and is incomplete inside an overlap scope. Wall-clock time is the comparison metric.

The small Metal event harness also passed independent source review and native compilation. Actual EOF before GO returned exit 2 with no completion marker. Hardware execution is still pending. Its simulated host failure is not a genuine GPU command failure; failed-command signal behavior and the effect of lower GPU signals after a CPU cleanup signal remain untested. END is emitted only after every committed command reaches a terminal status; otherwise the tool preserves a failure report and emits NOT_ENDED with dominant exit 3.

The separate full-model gate has compiled but remains under independent review. It requires all three fixed fixtures, 32 frozen output IDs, 31 continuations, full-vocabulary finite logits and strict normalized difference below 1e-4 against a fresh serial reference at Q4 width 32. ON and OFF must match every Float bit pattern, including signed zero, and their exact counters must match the declared execution. E4 batching with top-8 experts dispatches 60 GU, ACT and DN kernels and 240 ordered merges per token; counter expectations are derived from the actual schedule. Performance mode is allowed only after qualification, with one declared excluded warmup per arm and seven fixed AB/BA pairs per fixture, no adaptive exclusions, at least 2 percent gain and at most 5 percent spread in both arms for every fixture. Resource eligibility remains external and gainQualified is always false. Neither hardware qualification nor this matched performance experiment has run.
