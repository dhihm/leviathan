**Verdict: REQUEST_CHANGES.** Default-off behavior is preserved and the pure test suite is consistent with the shared types, but one lifecycle hole can hang the runner after a ticket failure, and the GPU-time accounting is mislabeled in exactly the way you asked me to flag. Nothing below is an execution claim. I have not compiled or run anything.

## Blocking

**1. Event value can regress after a failed drain, leaving a later wait unsatisfiable.** In `RouterOverlapTicketLedger.drain`, a failure raises the shared event to `lastCommittedSignal` via `unblock`. In-flight tickets that then complete still execute their own `encodeSignalEvent` with their lower values. Metal assigns the signaled value rather than taking a maximum, so the event can drop back below `lastCommittedSignal`. The ledger counter is never lowered and the state object is retained across scopes. The next `routerOverlapBeginSegment` encodes a wait on `lastCommittedSignal`, which may now never be reached, and the following `waitUntilCompleted` blocks forever. This can happen inside the same scope, because `routerOverlapDrainAll` records the failure but leaves `state.active` true, and in every later scope that reuses the state. Fix options, in order of preference: mark the state poisoned on any drain failure so every further overlap operation throws and `beginSegment` falls back to the plain flush-then-open path, and reallocate the event at the next scope entry; or, at minimum, re-raise `signaledValue` to `lastCommittedSignal` after the last `waitHandle` of a failing drain. The header comment already lists two untested event behaviors; this is a third and should be named there too.

## Required changes, non-blocking individually

**2. "GPU busy time" labeling.** `RouterOverlapTicketLedger`'s doc comment says time is accounted as "busy time, not utilization". Per your constraint, a ticket's `gpuStartTime..gpuEndTime` may include its encoded event wait and must not be called busy time. The runner also folds `outcome.gpuMicros` into `gpuMicrosTotal` in `routerOverlapRouterScores`, `routerOverlapDrainAll` and `routerOverlapDrainDiscarding`. That counter is documented as "cumulative GPU-busy microseconds" at `totalGpuMicros` and in the breakdown instrumentation comments, and it is what `executeGraphContinue` returns as `gpuMicros`. Inside the scope those readers are silently contaminated. Either accumulate ticket intervals in a separate `routerOverlapTicketMicros` counter, or document at every reader that scope-time values include event waits. Reword the ledger comment to "command-buffer interval, may include event wait".

**3. Header comment overclaims.** "Every command buffer opened while the scope is active encodes an explicit wait" is false for the direct synchronous path in `dispatch` and `dispatchPipeline`, which drain all tickets instead of waiting, and for the `beginSegment` fallthrough when an encoder is already open. Say "every deferred segment opened through `beginSegment`".

**4. `routerOverlapDrainAll` does not deactivate the scope on failure.** Even with item 1 fixed, after `discardOpenSegment` the token continues encoding into fresh segments with a recorded failure. The failure should end the token immediately; `state.active = false` or a poisoned flag is the simplest signal.

## Observations, no change required

- Default OFF: every new branch in `flushOpenSegment`, `discardOpenSegment`, `beginSegment`, `dispatch` and `dispatchPipeline` is behind `routerOverlapState != nil`, and `beginSegment` additionally requires `active`. With a nil state the incumbent paths are byte-for-byte unchanged. `engineIdentity` and `forge` only gain a throw when a scope is active.
- The ordering intent holds: R contains everything from the previous segment boundary through `router_proj`, S is exactly i1..i5, `router_topk` drains through R only, i10 opens a segment waiting on S. The `kind` label is asserted by the caller and only the plan's physical replay justifies that S never writes `bufRouter`; that is adequate for a diagnostic but worth stating in the read guard comment.
- Prepared SSA only, no model hashing, no promotion: `prepareRouterOverlapDiagnostic` goes through `prepare`, `routerOverlapPreflight` refuses raw or control execution in scope and diagnostic preparations outside it, and `forge` is refused. Static artifact constructors have no runner and cannot observe a scope, so no further guard is possible or needed there. The only hashing is one SHA-256 of the installed MoE kernel source at scope entry, never per token.
- Alias guard covers all runner buffers including expert scratch, MoE scratch, the statistics inverse buffer, frequency tables, weights and all KV caches. A statistics buffer reallocated mid-token after the preflight is a fresh allocation and cannot alias an existing live buffer.
- `discardOpenSegment` can now block on `waitUntilCompleted` when tickets are pending. Only inside a scope. Acceptable for a diagnostic, but note it in the function comment.
- `Gemma4Runner.forward` is not refused in scope. It produces no tickets so it is harmless, but it is a control execution that the preflight comment claims to refuse.
- `consistencyRejection` is never called by the runner. Consider asserting it in `routerOverlapVerifyToken`.
- Pure tests: I traced `testOrderedDrain`, `testFailedDrainContinues`, `testSequenceOverflow`, `testStepDerivation`, `testCandidates` (32 candidates, 5 eligible) and `testBindingFacts` (934 instructions) against the shared types and found the expectations consistent. The failure test only exercises the unblock callback, not the event regression in item 1, which needs a GPU test.
